# Avikus 부산사무소 ERP 요구사항 명세서

**작성일**: 2026-05-18  
**버전**: v1.0  
**작성자**: 구매팀  
**협업 대상**: 백엔드 개발자

---

## 1. 프로젝트 개요

### 1.1 목적
Avikus 부산사무소에서 사용하는 구매·자재·재고 관리 업무를 디지털화하여 팀 간 실시간 데이터 공유 및 업무 효율화를 달성한다.

### 1.2 현재 상태
- 프론트엔드 프로토타입 완성 (HTML/CSS/JS, localStorage 기반)
- 단일 PC에서 동작하는 오프라인 버전 운영 중
- 백엔드 서버 및 공유 DB 미구축 상태

### 1.3 목표 아키텍처
```
[사용자 PC / 태블릿]
       |
   브라우저 (Chrome)
       |
[프론트엔드 - HTML/JS]
       |  HTTP API (REST)
[백엔드 서버 - Node.js]  ← DELL XE3 서버 (부산사무소)
       |
[PostgreSQL DB]
```

## 2. 시스템 구조 (ERP 탭 구성)

하나의 웹 주소(예: `http://192.168.x.x:3000`)에 접속하면 아래 탭 구조로 운영된다.

```
부산사무소 ERP
├── [탭 1] 구매·자재관리     ← 현재 프로토타입 기능 전체
├── [탭 2] 출고·대여·검사요청 ← 재고 DB 기반 (신규 개발 예정)
├── [탭 3] FAT 관리          ← 호선·출고 DB 기반 (신규 개발 예정)
└── [공통] 대시보드          ← 전체 현황 요약 (추후)
```

## 3. 사용자 역할

| 역할 | 담당 업무 | 주요 사용 탭 |
|------|-----------|-------------|
| 구매팀 | PO 발행, 입고 처리, 출고 관리 | 탭 1, 탭 2 |
| 품질팀 | 입고 검수 확인, FAT 신청/완료 | 탭 1(Phase 4), 탭 3 |
| 설계팀 | 호선 등록, BOM 등록 | 탭 1(Phase 0) |
| 관리자 | 수기 재고 등록, DB 관리 | 전체 |

## 4. 기능 요구사항

### 4.1 탭 1 — 구매·자재관리 (현재 프로토타입 기준)

#### Phase 0 — 호선 등록 및 안전재고 관리
| 기능 | 설명 | 상태 |
|------|------|------|
| 호선 등록 | 신조/개조 선박 등록. 호선명, 계약일, 납품예정일 | ✅ 구현 | 설계
| 선급 등록 | 호선 등록 시 선급(KR/BV/DNV/LR/ABS/없음) 입력 | ⬜ 미구현 | 설계 
| BOM 등록 | 호선별 필요 HW 장비 목록 등록 (세대 템플릿 지원) | ✅ 구현 | 설계
| 안전재고 현황 | 호선별 필요 수량 vs 현재 재고 비교, 부족 알람 | ✅ 구현 | 설계가 기입한 내용을 바탕으로 생성된 DB
| 호선 특이사항 | 품질/납기/SW/기타 카테고리별 특이사항 등록 | ✅ 구현 |

#### Phase 1 — PO 발행
| 기능 | 설명 | 상태 |
|------|------|------|
| PO 발행 | PO Ref No. 자동생성(A-PO-YYNNNN), 업체 자동완성, 품목 라인 등록 | ✅ 구현 |
| PO QR 생성 | PO 정보 인코딩 QR 코드 생성 및 인쇄 | ✅ 구현 |
| PO 문서 출력 | Avikus 양식 Purchase Order PDF 출력 | ✅ 구현 |
| 업체 DB 관리 | 업체 코드/이름/이메일/연락처 등록·삭제 | ✅ 구현 |

#### Phase 2·3 — 입고 검수
| 기능 | 설명 | 상태 |
|------|------|------|
| PO QR 스캔 | 카메라 또는 수동 입력으로 PO QR 인식 | ✅ 구현 |
| 제품 QR 생성 | 단건 생성(인쇄 포함) / 일괄 생성+인쇄 | ✅ 구현 |
| S/N 팝업 입력 | 일괄 생성 시 수량만큼 S/N 개별 입력 팝업 | ✅ 구현 |
| 입고 검수 스캔 | 제품 QR 순차 스캔, 수량 카운팅, 중복 방지 | ✅ 구현 |
| 입고 완료 처리 | 완료 후 inventory DB 자동 저장, 서류 첨부 모달 | ✅ 구현 |

#### Phase 4 — Incoming Report 및 서류 관리
| 기능 | 설명 | 상태 |
|------|------|------|
| Incoming Report 생성 | Avikus 양식 PDF 출력 (A4 기준) | ✅ 구현 |
| 검사성적서 첨부 | 파일 업로드 → 해당 입고 건 전체 S/N 자동 연결 | ✅ 구현 |
| COC 첨부 | Certificate of Conformance 파일 업로드 | ✅ 구현 |
| 거래명세서 첨부 | 파일 업로드 | ✅ 구현 |
| 서류 현황 조회 | 입고 건별 서류 첨부 상태 확인 및 보기 | ✅ 구현 |

#### Phase 5 — 재고 현황
| 기능 | 설명 | 상태 |
|------|------|------|
| 재고 현황 조회 | S/N 단위 재고 전체 조회 | ✅ 구현 |
| 품목별 그룹 뷰 | 품목 코드별 요약 카드 + 상세 S/N 목록 (2단계) | ⬜ 미구현 |
| 출고 처리 | 재고 선택 → 출고, 상태 변경 + 이력 기록 | ✅ 구현 |
| 대여 처리 | 재고 선택 → 대여중, 상태 변경 + 이력 기록 | ✅ 구현 |
| 검사요청 처리 | 재고 선택 → 검사요청, 상태 변경 | ✅ 구현 |
| 수기 재고 등록 | 관리자 PIN 인증 후 직접 재고 등록 | ✅ 구현 |

### 4.2 탭 2 — 출고·대여·검사요청 (신규 개발)

> 현재 탭 1 Phase 5에 임시 구현된 기능을 전용 탭으로 분리

| 기능 | 설명 |
|------|------|

| 검사요청 목록 | 검사 진행 중인 제품 현황 |
| 반납 처리 | 대여 제품 반납 시 재고 상태 복원 |

---

### 4.3 탭 3 — FAT 관리 (신규 개발)

> FAT(Factory Acceptance Test): 선급이 있는 호선의 제품 출고 전 검사

| 기능 | 설명 |
|------|------|
| FAT 대상 자동 추출 | Phase 0에서 선급 입력된 호선의 제품 자동 분류 |
| 출고 예정일 입력 | 구매팀이 각 제품의 출고 예정일 입력 |
| FAT 기한 알림 | 접속 시 자동 체크: 출고일 30일 이내 → 팝업 알림 |
| FAT 완료 처리 | 완료 버튼 클릭 → 결과 문서 첨부 |
| FAT 이력 조회 | 호선별·제품별 FAT 완료 이력 |

**알림 구현 방식:**
- 현재(localStorage): 프로그램 접속 시 자동 체크 → 해당 건 팝업
- 서버 전환 후: 매주 월요일 구매팀·품질팀 이메일/슬랙 자동 발송

## 5. DB 테이블 명세

### 5.1 현재 테이블 목록

| 테이블명 | 설명 | 주요 필드 |
|---------|------|----------|
| `vessel_master` | 호선 마스터 | vessel_id, vessel_type, vessel_name, shipping_company, 선급(추가예정) |
| `vessel_bom` | 호선별 BOM | vessel_id(FK), item_code, item_name, required_qty |
| `vessel_notes` | 호선 특이사항 | vessel_id(FK), category, content, verified |
| `suppliers` | 업체 마스터 | supplier_code, supplier_name, supplier_email, supplier_tel |
| `po_header` | 발주서 헤더 | po_id, po_ref_no, supplier_code, vessel_name, issue_date, due_date, pic, status |
| `po_line` | 발주서 라인 | line_id, po_id(FK), item_code, description, ordered_qty, unit, unit_price |
| `inventory` | 재고 (S/N 단위) | mc_code, item_code, serial_no, po_id(FK), incoming_date, status, cert_id(FK) |
| `incoming_header` | 입고 헤더 | incoming_id, po_id(FK), incoming_date, ordered_qty, total_scanned, status |
| `incoming_line` | 입고 라인 | scan_id, incoming_id(FK), mc_code, item_code, serial_no |
| `inspection_cert` | 첨부 서류 | cert_id, incoming_id(FK), cert_no, file_name, file_data, coc_file_name, trade_file_name |
| `outgoing_log` | 출고/대여 이력 | log_id, inv_mc, inv_sn, action, vessel_id, date, note |

### 5.2 추가 예정 테이블

| 테이블명 | 설명 |
|---------|------|
| `fat_master` | FAT 관리 (vessel_id, item_code, planned_ship_date, fat_status) |
| `fat_documents` | FAT 결과 문서 첨부 |
| `item_master` | 품목 코드 마스터 (품목 코드, 품목명, 카테고리) |

## 6. API 명세 (서버 전환 후 구현 예정)

> 현재 `js/db.js` (localStorage) → 서버 전환 시 `js/api.js` (REST API)로 교체

### 기본 규칙
- Base URL: `http://{서버IP}:3000/api`
- 응답 형식: JSON
- 인증: 추후 JWT 토큰 방식 (1차 배포는 IP 기반 접근 제한)

### 주요 엔드포인트 (예시)

```
[호선]
GET    /api/vessels          호선 전체 조회
POST   /api/vessels          호선 등록
DELETE /api/vessels/:id      호선 삭제

[PO]
GET    /api/po               PO 전체 조회
POST   /api/po               PO 등록
GET    /api/po/:id/lines     PO 라인 조회

[재고]
GET    /api/inventory        재고 전체 조회
GET    /api/inventory/:item  품목별 재고 조회
PATCH  /api/inventory/:mc    재고 상태 변경 (출고/대여/검사요청)

[입고]
POST   /api/incoming         입고 완료 처리
GET    /api/incoming/:id     입고 상세 조회

[서류]
POST   /api/documents        서류 첨부 (Base64 → 파일 저장)
GET    /api/documents/:inc   입고별 서류 조회
```

## 7. 비기능 요구사항

| 항목 | 요구사항 |
|------|---------|
| 접속 환경 | 사내 네트워크(LAN) 내 Chrome 브라우저 |
| 동시 접속 | 최소 5명 동시 사용 가능 |

| 파일 첨부 | 성적서·COC·거래명세서 PDF/이미지, 건당 최대 10MB |

| 오프라인 | 서버 장애 시 localStorage 폴백 고려 (추후) |
