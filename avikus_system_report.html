현재 상태 & 전환 목표
1.1 현재 상태 (프론트엔드 프로토타입)
프론트엔드(HTML/CSS/JS)는 기능 구현 완료 상태입니다. 데이터는 현재 브라우저의 localStorage에 저장되며, 단일 PC에서만 동작합니다. 백엔드 개발자가 할 일은 이 프론트엔드가 사용하는 데이터 구조 그대로 API와 DB를 구현하는 것입니다.
항목현재 (프로토타입)목표 (서버 전환 후)

동시 접속불가 (1명)팀 전체 동시 접속

ERP 시스템 구조
2.1 단일 웹 — 탭별 기능 분리 구조
핵심 설계 원칙: 하나의 웹 주소(http://서버IP:3000)에 접속하면 ERP 전체를 사용합니다. 각 기능은 탭으로 분리되며, 모두 동일한 PostgreSQL DB를 공유합니다. 별도 도메인(purchase.xxx.com, stock.xxx.com)으로 쪼개지 않습니다.
부산사무소 ERP (http://192.168.x.x:3000) │ ├── [탭 1] 구매·자재관리 ← 현재 프로토타입 전체 (Phase 0~4) │ ├── Phase 0 — 호선·BOM·안전재고 │ ├── Phase 1 — PO 발행·QR 생성 │ ├── Phase 2·3 — 입고 검수·스캔 │ ├── Phase 4 — Incoming Report·서류 관리 │ └── Phase 5 — 재고 현황 │ ├── [탭 2] 출고·대여·검사요청 ← 신규 개발 (재고 DB 기반) │ ├── 출고 처리 & 이력 조회 │ ├── 대여 현황 & 반납 처리 │ └── 검사요청 현황 │ ├── [탭 3] FAT 관리 ← 신규 개발 (호선·출고 DB 기반) │ ├── FAT 대상 자동 추출 (선급 있는 호선) │ ├── 출고 예정일 입력 │ ├── 기한 알림 (접속 시 팝업 + 주간 이메일) │ └── FAT 완료 처리 & 문서 첨부 │ └── [공통] PostgreSQL DB └── 모든 탭이 동일한 DB 사용
2.2 서버 아키텍처
[사용자 PC / 태블릿] │ Chrome 브라우저 ▼ [프론트엔드] index.html + CSS/JS (정적 파일 서빙) │ HTTP REST API (JSON) ▼ [백엔드] Node.js + Express (DELL XE3, 포트 3000) │ ├── /api/vessels 호선·BOM ├── /api/po PO 발행 ├── /api/incoming 입고 처리 ├── /api/inventory 재고 관리 ├── /api/documents 서류 첨부 ├── /api/outgoing 출고·대여 └── /api/fat FAT 관리 (예정) │ ▼ [PostgreSQL] DB: avikus_erp (DELL XE3) │ └── /uploads/ 첨부파일 저장 폴더

PO 상태 업데이트 UPDATE po_header SET status = 'COMPLETE' WHERE po_id = ? COMMIT // 실패 시 ROLLBACK
5.2 PO 번호 자동채번 — 동시성 처리
// GET /api/po/next-ref-no — 동시 접속 시 중복 방지 // 방법 1: SELECT FOR UPDATE (간단) SELECT MAX(po_ref_no) FROM po_header WHERE po_ref_no LIKE 'A-PO-26%' FOR UPDATE // 방법 2: 별도 시퀀스 테이블 (권장) CREATE TABLE po_sequence (year CHAR(2) PRIMARY KEY, last_seq INTEGER); // INSERT ... ON CONFLICT DO UPDATE 로 원자적 증가
5.3 안전재고 현황 계산 — 서버 집계
// GET /api/safety-stock 쿼리 예시 SELECT v.vessel_name, b.item_code, b.item_name, b.required_qty, COUNT(i.mc_code) FILTER (WHERE i.status = 'IN_STOCK') AS current_stock, b.required_qty - COUNT(i.mc_code) FILTER (WHERE i.status = 'IN_STOCK') AS shortage FROM vessel_bom b JOIN vessel_master v ON b.vessel_id = v.vessel_id LEFT JOIN inventory i ON b.item_code = i.item_code GROUP BY v.vessel_name, b.item_code, b.item_name, b.required_qty
5.4 FAT 알림 스케줄러
// 매주 월요일 09:00 자동 실행 (node-cron) cron.schedule('0 9 * * 1', async () => { // 출고 예정일 30일 이내 FAT 미완료 건 조회 const targets = await db('fat_master') .where('fat_status', 'PENDING') .whereRaw('planned_ship_date <= NOW() + INTERVAL \'30 days\'') // 구매팀·품질팀에 이메일/슬랙 발송 await sendAlert(targets) })

파일 저장 전략
현재 문제: localStorage에 PDF를 Base64로 저장하면 파일 1개당 1~3MB 소모. localStorage 한도는 5~10MB → 파일 3~4개 첨부 후 저장 실패 위험.
서버 전환 시 반드시 파일시스템 저장으로 변경해야 합니다.
방식장점단점권장
DB BLOB 저장 단순, 백업 통합 DB 부하, 느린 조회, 용량 폭증 ❌ 비권장
서버 파일시스템 (/uploads) 빠른 전송, DB 부하 없음, 용량 무제한 파일-DB 일관성 관리 필요 ✅ 권장
외부 스토리지 (S3 등) 확장성 사내망 환경에서 불필요 ❌ 불필요 (사내망)
권장 폴더 구조
/uploads/ ├── cert/ 검사성적서 예: CERT-INC-xxx-20260519.pdf ├── coc/ COC 예: COC-INC-xxx-20260519.pdf ├── trade/ 거래명세서 예: TRADE-INC-xxx-20260519.pdf └── fat/ FAT 결과문서 예: FAT-xxx-20260519.pdf
Multer 설정 예시 (Node.js)
const multer = require('multer') const storage = multer.diskStorage({ destination: (req, file, cb) => { const typeMap = { cert_file: 'cert', coc_file: 'coc', trade_file: 'trade' } cb(null, `/uploads/${typeMap[file.fieldname]}`) }, filename: (req, file, cb) => { const name = `${file.fieldname.toUpperCase()}-${req.params.incoming_id}-${Date.now()}.pdf` cb(null, name) } }) // DB에는 경로만 저장: '/uploads/cert/CERT-INC-xxx-1716000000.pdf'

백엔드 개발자 사전 고민 Q&A
Q1
QR 코드 생성을 서버에서 해야 하나요, 프론트에서 해야 하나요?
현재 프론트엔드(jsQR 라이브러리)에서 생성합니다. 서버 전환 후에도 프론트에서 생성하는 게 유리합니다.
✅ 결론: 프론트엔드에서 계속 생성
QR 코드 인코딩 데이터는 PO ID, S/N 등 DB에서 가져온 값들의 조합입니다. 서버가 QR 이미지를 만들 필요 없고, 프론트가 데이터를 받아 qrcode 라이브러리로 렌더링합니다. 서버는 데이터 제공만 하면 됩니다.
Q2
인증은 어떻게 해야 하나요? 사내망이라 복잡한 인증이 필요한가요?
사내 LAN 전용 시스템입니다. 외부 접속은 없습니다.
✅ 1차: IP 기반 접근 제한 (가장 단순)
서버에서 사내 IP 대역(예: 192.168.x.x)만 허용. 별도 로그인 없이 접속 가능.
2차 (고도화 시): 팀별 PIN 또는 간단한 JWT 로그인
구매팀 / 품질팀 / 설계팀 권한 분리가 필요해지면 그때 추가.
Q3
2,000개 이상의 재고 데이터를 어떻게 효율적으로 조회하나요?
Phase 5 재고 현황에서 전체를 한 화면에 보여주면 성능 문제가 발생합니다.
✅ 2단계 뷰 + 페이지네이션으로 해결
1단계: 품목 코드별 집계 요약 (GET /api/inventory/summary) — 30개 품목이면 30줄만 표시
2단계: 특정 품목 클릭 시 해당 품목 S/N 목록 페이지네이션 (limit=50)
inventory 테이블에 item_code, status, incoming_date에 인덱스 추가.
Q4
localStorage 데이터를 서버 DB로 어떻게 마이그레이션하나요?
현재 운영 중인 데이터(호선, PO, 재고 등)를 서버 DB로 옮겨야 합니다.
✅ JSON Export → 서버 Import 스크립트 방식
① 프론트에서 "전체 데이터 JSON 내보내기" 버튼 → 브라우저 다운로드
② 서버에 import.js 스크립트 작성 → JSON을 읽어 PostgreSQL에 INSERT
③ 마이그레이션 완료 후 localStorage 초기화
주의: inspection_cert의 file_data(Base64) → 서버에 파일로 저장 후 경로로 교체 필요.
Q5
Incoming Report PDF를 서버에서 생성해야 하나요?
현재는 프론트에서 HTML로 렌더링 후 브라우저 인쇄(Ctrl+P)로 PDF를 만듭니다.
✅ 1차: 프론트 렌더링 + 브라우저 인쇄 유지
서버에서 Puppeteer 등으로 PDF 생성하는 건 복잡도가 높습니다. 현재 방식(HTML 렌더링 → 브라우저 인쇄)이 품질도 좋고 수정도 쉽습니다.
2차 (자동화 필요 시): Puppeteer로 서버 PDF 생성 → 파일 저장 → 다운로드 링크 제공.
Q6
여러 명이 동시에 같은 재고에 출고 처리하면 어떻게 됩니까?
A팀원이 S/N-001을 출고 처리하는 동시에 B팀원도 같은 S/N-001을 출고 처리하는 경우.
✅ DB 트랜잭션 + 상태 체크로 해결
POST /api/outgoing 처리 시:
① SELECT status FROM inventory WHERE mc_code = ? FOR UPDATE
② status = 'IN_STOCK' 인 경우만 진행, 아니면 409 Conflict 반환
③ UPDATE inventory SET status = 'SHIPPED' ...
프론트엔드는 409 응답 시 "이미 다른 사람이 처리한 재고입니다" 메시지 표시.
Q7
현재 프론트코드에서 DB 접근 방식이 어떻게 달라지나요?
프론트엔드 js/db.js가 localStorage를 직접 읽는데, 서버 전환 시 어떻게 바꿔야 하나요?
✅ js/db.js → js/api.js 파일 하나만 교체하면 됩니다
현재 설계가 이를 위해 localStorage 코드를 db.js 하나에 집중시켜 놓았습니다.
DB.po_header.push(item) → await API.post('/api/po', item)
phase0~5.js는 수정 불필요. db.js를 api.js로 교체하고 비동기(async/await) 처리만 추가.

9.2 API 연동 시 주의사항
항목현재 (localStorage)서버 전환 후
데이터 저장 DB.po_header.push(item); dbSave('po_header') await fetch('/api/po', {method:'POST', body: JSON.stringify(item)})
파일 첨부 FileReader → Base64 → localStorage FormData → multipart/form-data → POST /api/documents
ID 생성 프론트의 uid() 함수로 생성 서버 DB에서 생성 후 응답에 포함 (PO 번호는 서버 채번 필수)
CORS 해당없음 Express CORS 미들웨어 필요 (개발 시 모든 origin, 운영 시 사내 IP만)
에러 처리 없음 모든 API 응답에 try-catch + 표준 에러 형식 적용
